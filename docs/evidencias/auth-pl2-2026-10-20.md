Casos relevantes verificados:

- Login con CSRF y origen válidos emite cookie sin devolver `idToken` ni
  contraseña.
- Token CSRF anterior al login deja de servir.
- Usuario deshabilitado no recibe cookie de sesión.
- Un fallo de la auditoría obligatoria impide entregar la sesión.
- Viewer recibe 403 en usuarios, auditoría y mutaciones de sesión.
- Admin lista usuarios y eventos, y puede crear/actualizar con CSRF.
- La creación repetida no duplica identidad, perfil, operación ni auditoría.
- Un conflicto de correo no adopta una identidad ajena.
- Un fallo de sincronización con Auth deja la operación reintentable y responde
  `503 AUTH_SYNC_PENDING`; la auditoría `user.update` ya quedó escrita una sola
  vez en la transacción del perfil y no se duplica al reintentar.
- Un `PATCH` de `enabled:false` con otra actualización pendiente se aplica: la
  operación anterior pasa a `superseded` y la nueva completa el perfil y Auth.
- La recuperación usa el perfil vigente: una operación antigua no reactiva una
  cuenta ya deshabilitada.
- El reintento de creación responde `409 IDEMPOTENCY_CONFLICT` si el usuario
  cambió de nombre o fue deshabilitado después de crearse.
- Dos recuperadores concurrentes se serializan por usuario y aplican la
  identidad una sola vez.
- La recuperación completa una actualización pendiente y omite una creación sin
  contraseña.
- Con Firebase Auth Emulator real, un cambio de rol actualiza
  `customClaims.role` y un cambio de habilitación marca `disabled:true`; el
  login posterior devuelve `USER_DISABLED` y la cookie deja de verificar.
- La apertura de expediente se registra una sola vez; el polling no genera
  eventos nuevos.

`localhost:5173`, con emuladores limpios.

Flujo ejecutado:

2. La aplicación redirige a `/login` tras resolverse `GET /auth/me` con 401.
3. Enviar credenciales del fixture admin local.
4. La aplicación vuelve a `/monitoring`, no a una ruta externa.

   `Correo o contraseña incorrectos.` en un elemento `role="alert"` y deja el

## Limitaciones y pendientes

La simplificación posterior reutiliza `LoadingState`, `ErrorState`, `AuthUser`
y `requireRole`. Typecheck global, build web y las 12 pruebas afectadas de
usuarios/auditoría y protección de la aplicación volvieron a pasar; no se eliminaron pruebas.

- No se ejecutó contra Firebase Standard real ni se desplegó.
- El emulador no demuestra que los índices compuestos estén disponibles en un
  proyecto real.
- Corrección de P-06: la prueba anterior no separaba emisión y revocación por
  más de un segundo. Con 1200 ms y la identidad aún habilitada, la suite
  correctiva produjo `cookieRejectedAfterRevocation=true`. No se sostiene la
  conclusión anterior de que el emulador ignore la revocación.
- El Auth Emulator ignora `customClaims` enviado dentro de `updateUser`; el
  adaptador usa `setCustomUserClaims` y la evidencia comprueba el claim con
  `getUser`.
- La creación de usuarios no puede detectar como conflicto un cambio de
  contraseña con el mismo correo, nombre y rol, porque la contraseña no se
  persiste ni se deriva.
- Una creación pendiente sin identidad Auth exige que el cliente reintente con
  la contraseña.
- La matriz completa de permisos de pacientes, placas y asignaciones sigue
  dependiendo de los endpoints de #26/#27.
- El PR #38 ya está fusionado y se incorporó localmente mediante avance rápido.
  Se resolvió la cabecera conservando navegación administrativa, Monitoreo,
  perfil y logout; las rutas usan la misma caché y el hook compartido de sesión.
- El script de lint de los workspaces es un marcador; no ejecuta un linter real.
